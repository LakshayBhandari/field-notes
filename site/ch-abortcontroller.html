AbortController in useEffect

AbortController is a tiny browser API: you make one, hand its .signal to fetch, and later call .abort() to cancel that request. When aborted, the fetch promise rejects with a DOMException named AbortError.

In a data-fetching effect, you create a fresh controller per run, pass the signal to every fetch, and abort it from the effect's cleanup function. React runs cleanup before the effect re-runs (deps changed) and when the component unmounts — so the previous, still-in-flight request gets cancelled the moment a new one starts.

useEffect(() => {
  const controller = new AbortController();

  fetch(url, { signal: controller.signal })
    .then(r => r.json())
    .then(setData)
    .catch(err => {
      if (controller.signal.aborted) return; // expected — not a real error
      setError(err.message);
    });

  return () => controller.abort(); // cleanup: cancel the stale request
}, [url]);

Note the catch guard: an abort rejects the promise, so without the controller.signal.aborted check your error UI would light up on every refetch. Abort is a client-side concern — it stops you from reading the response; the server may still finish the work.

⚠️ IMPORTANT

Common misread: "The cleanup/abort is just to silence React's old can't setState on an unmounted component warning — React 18 dropped that warning, so I can skip it."

Actually: the real bug it kills is a race between overlapping requests. Fire request A, change the input, fire request B — if A is slower it can resolve after B and overwrite the newer data with stale data. Order of arrival ≠ order of dispatch. Aborting A on cleanup guarantees the latest request wins.

Why it matters: refetch buttons and changing dependencies spawn overlapping requests constantly. The symptom is old data intermittently flashing in over new data — non-deterministic, network-timing-dependent, and nearly impossible to reproduce on demand. Cleanup makes it structurally impossible.
