Widget CSS survival rules: px and max z-index

A Shadow DOM seals the 44Com widget's styles off from the host page — but two things still leak through the boundary or fight the widget from outside it. Both have blunt, non-negotiable fixes.

Rule 1 — size in px, never rem. rem resolves against the host page's root <html> font-size, which you don't control and can't see through the shadow boundary. A host with html { font-size: 30px } would blow your whole widget up 2×. px is absolute — a fixed number of device pixels — so it renders the same on every host.

/* widget CSS (injected into the shadow root) */
.bubble { width: 56px; height: 56px; }   /* ✅ px — immune to host */
/* .bubble { width: 3.5rem; }               ❌ rem — scales with host's root */

Rule 2 — z-index: 2147483647 on the bubble/panel. That's the 32-bit signed max. The hostile test page had a z-index: 999999 overlay bar; a real site might have sticky headers, cookie banners, modal backdrops. Stacking context is a page-level concern — the shadow boundary does not isolate it — so your floating widget must claim the top of the stack to guarantee nothing covers it.

.bubble, .panel { z-index: 2147483647; }  /* max — nothing sits above it */
⚠️ IMPORTANT

Common misread: "the widget is in a shadow root, so units and stacking are isolated too — I can use rem and a normal z-index."

Actually: Shadow DOM isolates which CSS rules apply, not how values resolve or how layers stack. rem still resolves against the host's root font-size, and z-index competes in the page's global stacking context. Use px for all widget sizing, and the max z-index (2147483647) on anything that floats over the page.

Why it matters: these are the two leak vectors that survive a "sealed" shadow root. A widget that looks perfect on your clean test page can render giant, or vanish behind a cookie banner, on a real customer's site — the exact failures a hostile host page is built to catch early.
