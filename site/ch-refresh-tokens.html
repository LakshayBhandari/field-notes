Refresh tokens: storage, transport, and the rotation gap

The JWT chapter answered why there is a second token at all — the access JWT can't be revoked, so a revocable companion is bolted alongside. This chapter is about the three concrete questions that follow: how is the refresh token stored, how is it transported, and what breaks because there's no rotation yet.

The whole picture in one diagram

┌──────────────────────────────── browser ───────────────────────────────────┐
│                                                                            │
│   React memory:   accessToken (JWT, 15m)   ← readable by JS                │
│                                                                            │
│   Cookie store:   refreshToken cookie       ← httpOnly: JS CANNOT read it  │
│                                                                            │
└────────────┬───────────────────────────────────────────────┬───────────────┘
             │ Authorization: Bearer <access>                │ Cookie sent
             │ (added by fetch)                              │ automatically
             ▼                                               ▼
┌───────────────────────────────── server ───────────────────────────────────┐

│                     no DB lookup — stateless                               │

Storage: why the refresh token is hashed in db.sessions

Look at a row in db.json: tokenHash is a sha256 digest. The raw refresh token never touches the disk. The threat model is the same as passwords — a database leak — and the defence is the same: store only a one-way derivative.

WITHOUT hashing (raw token in db.sessions):
─────────────────────────────────────────────
attacker steals db.json   →   gets ready-to-use refresh tokens for
                              every active session   →   paste into
                              the Cookie header   →   instantly is
                              every logged-in user, for up to 7 days

WITH hashing (tokenHash = sha256(refresh)):
─────────────────────────────────────────────
attacker steals db.json   →   gets a list of sha256 digests   →
                              cannot reverse a hash   →   has nothing
                              they can actually replay against /refresh

Why fast hashing here (sha256), but slow (bcrypt) for passwords

The principle "never store the raw secret" is the same; the choice of hash is different because the inputs are wildly different in entropy.

PASSWORD                                REFRESH TOKEN (JWT)
─────────────────────────               ────────────────────────────
"hunter2"                               eyJhbGciOiJIUzI1NiIs…
~10 chars, human-chosen                 hundreds of chars,
~30 bits of entropy                     random + signed
                                        hundreds of bits of entropy
GUESSABLE in days on a GPU              UNGUESSABLE before the heat
                                        death of the sun
↓                                       ↓
must use a SLOW hash so each            a FAST hash is fine — nobody is
guess is expensive (bcrypt at           guessing this; the only thing
cost 10 → 2¹⁰ iterations)               the hash defends against is a
                                        leak being directly replayable

Rule of thumb: fast hash is safe when the input itself is high-entropy / random. Slow hash earns its keep only when the input is something a human picked.

Transport: httpOnly cookie vs JS memory — two different attacks

The access token sits in React state. The refresh token sits in an httpOnly cookie. The asymmetry is deliberate, and the two cookie flags involved defend against two different attacks. Do not blur them.

           XSS attack                          CSRF attack
           ────────────                         ────────────
attacker  injects a <script> into            tricks the user's browser into
          your page (e.g. via a               firing a request at your API
          vulnerable dependency,              from a different origin
          stored XSS, etc.)                   (evil.com submits a hidden
                                              form to your-api.com)
goal      read tokens out of the              ride along on credentials
          page and exfiltrate them            the browser auto-attaches
defends?
 ─ access token in memory   ✅ JS can read it, but it dies on tab close;
                               narrow window. localStorage would be worse —
                               persistent and JS-readable.
 ─ refresh token in cookie  ✅ with httpOnly: JS literally CANNOT read it.
                               The browser sends it; scripts never touch it.
                             ✗  without httpOnly: the cookie is JS-readable,
                               same risk as localStorage.

 ─ refresh token in cookie  ✗ httpOnly doesn't help — the browser auto-sends
                               cookies cross-origin (which is the attack).
                             ✅ sameSite: lax/strict blocks the cross-origin
                               send → CSRF defeated.

TL;DR  httpOnly  →  defends against XSS reading the cookie.
       sameSite  →  defends against CSRF auto-sending the cookie.
       Two flags, two attacks. Both are set on the refresh cookie.

Inside /refresh: signature is integrity, the DB row is liveness

The route does two distinct checks. They feel redundant until you ask "what could a valid-signature-but-stale-row mean?"

step 1 — jwt.verify(refresh, JWT_REFRESH_SECRET)
         proves: the token was issued by US, has not been tampered,
                 has not expired.
         does NOT prove: that we still consider it valid right now.

step 2 — look up db.sessions for the row referenced by decoded.sessionId
         AND require tokenHash == sha256(refresh)
         proves: this exact token still corresponds to a live session
                 (nobody hit /logout, /devices, or /logout-all).

what step 2 catches that step 1 cannot:
─────────────────────────────────────────
  • user clicked logout 2 minutes ago  → session row deleted, sig still valid
  • another device revoked this session → same
  • /logout-all after suspected breach   → same
  • refresh token came from a stale db backup → sessionId would match
                                                 but tokenHash would not

SIGNATURE  proves the token wasn't TAMPERED.
DB ROW     proves the token wasn't REVOKED.
You need both, because they answer different questions.

The rotation gap — what's missing, and the attack it enables

/refresh currently mints a new access token but reuses the same refresh token for the full 7 days. That's the gap. With rotation, every /refresh call would invalidate the old refresh token (delete + recreate the session row with a new hash) and return a brand-new refresh cookie. Why does this matter? Walk through the same attack twice:

SCENARIO   attacker steals user's refresh token on day 1 (via malware,
           shared machine, leaked cookie, etc.). User keeps using the app.

WITHOUT ROTATION (today)
─────────────────────────
  day 1   attacker pastes the stolen cookie into their browser
          → /refresh succeeds → issues access token → they're you
  day 2   user uses the app: /refresh succeeds with the SAME token
          → fresh access token → they're still you
  …       both copies of the same token work independently for 7 days.
          The DB sees identical hash + sessionId both times.
          NOBODY NOTICES. Attacker has 7 days of silent access.

WITH ROTATION
─────────────
  day 1   attacker calls /refresh first.
          server rotates: deletes old session row,
                          inserts new row with new tokenHash,
                          sets new refresh cookie on attacker's browser
  day 2   user calls /refresh with the *original* refresh token.
          jwt.verify   ✅  (sig still valid — it WAS issued by us)
          sessions row with that sessionId still exists ✅
          tokenHash matches?  ❌  (we rotated to a new hash)
          → /refresh fails for the real user.
          → user is forced to log in again.
          → user notices the anomaly.

  flipped: if the user refreshes first, the attacker's stolen token
           becomes the one that fails the tokenHash check next time.
           Either way, the *first reuse of the now-rotated token* is
           the signal: someone has it who shouldn't.

The pattern is called rotation with reuse detection.
The fact that an old token was presented at all is the alarm.

Adding it is one block of code: in /refresh, after the checks pass, delete the existing session row, sign a new refresh JWT, insert a new row, set a new cookie. The architecture already has the place to record state — rotation just uses it.

⚠️ IMPORTANT

Common misread: "We hash the refresh token in db.sessions because it's a secret and bcrypt does that for passwords too."

Actually: we hash it for the same threat (DB leak) but with a fast hash (sha256), not bcrypt. Refresh tokens are hundreds of bits of random entropy — nobody is brute-forcing them, so slowness adds nothing. The hash exists purely so a stolen db.json isn't a stash of ready-to-replay tokens.

Why it matters: the rule is "fast hash is safe when the input itself is unguessable" — passwords need slow hashing because they are guessable, refresh tokens don't because they aren't.

⚠️ IMPORTANT

Common misread: "httpOnly on the refresh cookie is what stops CSRF."

Actually: httpOnly stops XSS from reading the cookie (JS can't see it at all). CSRF — where the browser is tricked into auto-sending the cookie cross-origin — is stopped by sameSite: lax (or strict). Two flags, two attacks; conflating them leaves one side wide open.

Why it matters: if you ever remove sameSite "because we already have httpOnly", you've quietly re-opened CSRF. They are not substitutes.

⚠️ IMPORTANT

Common misread: "Once jwt.verify passes on the refresh token, we don't really need to hit the DB."

Actually: jwt.verify proves the token wasn't tampered. It cannot prove it wasn't revoked — a logout 30 seconds ago leaves the signature mathematically perfect. The DB row check is the only thing that turns a valid signature into a live session.

Why it matters: without that lookup, /logout, /devices/:id, and /logout-all are decorative — the refresh token would keep working until its 7-day exp passed.

⚠️ IMPORTANT

Common misread: "Without rotation, a stolen refresh token isn't much of a problem — the attacker still has to use it."

Actually: the same refresh token works for both attacker and real user for its full 7-day lifetime, both can call /refresh independently, and the server cannot tell their requests apart (identical sessionId + tokenHash). Nothing flags the duplicate use. Rotation is what turns "an old token was presented" into a detectable anomaly.

Why it matters: rotation isn't a polish item — it's the mechanism that gives you any chance of noticing a compromise mid-session. Without it, the only signal is the user reporting weirdness.

🔄 ROLLING-SESSION CAVEAT

The rotation gap came up only at the end of the grilling round, and only in passing. Without this note, future-me is likely to "explain refresh tokens" by describing the current code as the finished design, instead of as the 80% version that's still missing rotation + reuse detection.
