OAuth 2.0 sign-in (GitHub + Google)

"Sign in with GitHub / Google" is the Authorization Code flow. The job is to prove to your backend that the person clicking the button controls a particular GitHub/Google account, without your app ever seeing their GitHub/Google password. Once that proof lands, you reuse your existing session machinery (JWT access + refresh cookie + sessions row) to log them in.

The dance, end to end

 Browser              Your backend             Provider (GitHub/Google)
    │                       │                         │
    │  click "GitHub"       │                         │
    ├──[GET /auth/github]──→│                         │
    │                       │ set oauth_state cookie  │
    │                       │ build authorize URL     │
    │ ←──[302 redirect]─────┤                         │
    │                                                 │
    ├──[GET authorize?client_id=…&state=X&scope=…]───→│
    │                                                 │ user authorizes
    │ ←─────────[302 /auth/github/callback?code=Y&state=X]──┤
    │                       │                         │
    ├──[GET /callback?code=Y&state=X]──→              │
    │                       │ cookie==state ?         │
    │                       ├──[POST token, code=Y]──→│
    │                       │ ←──[access_token]───────┤
    │                       ├──[GET /user]───────────→│
    │                       │ ←──[profile]────────────┤
    │                       │ findOrCreateUser(...)   │
    │                       │ issueSession(...)       │  ← our JWT + refresh cookie
    │ ←──[302 /auth/callback#token=eyJ…]──┤           │
    │                                                 │
    │ SPA reads location.hash, calls /me, shows welcome

Two redirects send the browser to the provider and back, two server-to-server calls swap the short-lived code for a profile, then a final redirect drops the user back on the SPA carrying our own session — not the provider's token.

Why a backend at all (and not pure SPA)

The token exchange call needs the client_secret. That secret cannot live in the browser — any user could read it from devtools and impersonate your app. So the swap must happen server-side. Pure-SPA flows exist (PKCE) but if you already have a backend, classic server-side Authorization Code is simpler and the secret stays out of users' hands.

The state cookie: login-CSRF defence

Before redirecting to the provider, the backend generates a random state, stores it in an httpOnly cookie on the victim's browser, and sends the same value in the authorize URL. On the callback, it compares the cookie to ?state=…. Mismatch → reject. Match → trust that the same browser that visited /auth/github is the one finishing the callback.

Without state, this attack works:

 Attacker                                    Victim
    │                                            │
    │ starts OAuth with THEIR own GitHub         │
    ├──[/auth/github]→ … →[authorize on GH]─┐    │
    │ ←──[callback?code=Y_attacker]─────────┘    │
    │ intercepts code Y (never lets it complete) │
    │                                            │
    │ crafts: yourapp.com/auth/github/callback?code=Y_attacker
    │             │                              │
    │             └──[phishing img/link]───────→ │ (loads while logged in)
    │                                            ├──→ your backend
    │                                            │   processes attacker's code
    │                                            │   links ATTACKER's GitHub to
    │                                            │   VICTIM's user row
    │                                            │
    │ attacker can now sign in with their own GitHub → lands in victim's account

With state: the victim's browser has no oauth_state_github cookie matching state=X → callback aborts → attack neutralised. SameSite=Lax on the cookie means it's automatically scoped to flows the victim initiated, never sent on cross-origin background loads.

⚠️ IMPORTANT

Common misread: "The state parameter is a nonce that just stops random people from hitting our callback URL."

Actually: state defends against login-CSRF — the attacker tricking the victim's browser into completing the attacker's OAuth flow, which would silently link the attacker's social account to the victim's session. The threat isn't "spam on the callback"; it's "your account is now also signable-into by a stranger's GitHub."

Why it matters: if you ever think "we don't really need state, who's going to forge a callback?", you've just argued yourself into a silent-takeover hole. Both the cookie and the query param are required — same value, two channels, one check.

The emailVerified gate: link-by-email safety

When the same person signs up by password first and later clicks "Continue with GitHub" (or vice versa), you want one account, not two. The standard pattern is "if there's already a user with this email, link the new identity to that user." That sounds harmless until you remember that GitHub and Google both let users add an email without verifying it.

  Without the emailVerified gate
  ──────────────────────────────────────────────────────────
   victim has password account: { id: 1, email: "v@x.com" }
   attacker creates GitHub acct, adds email "v@x.com",
     DOES NOT verify it (just leaves it as pending)
   attacker clicks "Continue with GitHub" on your app
     callback gets profile { email: "v@x.com" }
     findOrCreateUser does users.find(email = "v@x.com")
     → returns USER 1 (the victim)
   attacker is now logged in as the victim         ❌

  With the emailVerified gate
  ──────────────────────────────────────────────────────────
   same attacker flow → profile.emailVerified === false
   findOrCreateUser skips the link-by-email branch
     → creates a brand new, separate user for the attacker
   victim's account untouched                       ✓

GitHub marks an email verified: true only after a confirmation link in that inbox is clicked — same for Google. So emailVerified is the provider saying "we actually saw the owner of this address." Without that gate, "sign in with GitHub" becomes "sign in as anyone whose email I can guess."

⚠️ IMPORTANT

Common misread: "If GitHub returns an email for the user, I can trust it enough to merge with an existing account."

Actually: the provider returning the email is not proof of ownership. You can only trust it for linking when email_verified (Google) or the matching row's verified: true (GitHub's /user/emails) is set. Anything else and you must create a separate user, not merge.

Why it matters: conflating "email exists on the profile" with "email belongs to this person" turns OAuth into a free account-takeover primitive — type your victim's email into any new social account, click the button, you're in. The gate is the only thing between "social login" and "anyone can become anyone."

Where it slots into the existing session system

The OAuth callback ends by calling the same issueSession(user, request, response, db) that /login uses for passwords. That means everything downstream — JWT access tokens, the httpOnly refresh cookie, the sessions row, "log out everywhere" — keeps working unchanged. OAuth doesn't replace the auth system; it's an additional way to land in it.

  users                          identities                   sessions
  ─────                          ──────────                   ────────
   id ◄────────────────────┐     id                       ┌──► id
   email                   │     userId  ──────────────── │    userId ─┐
   password (nullable)     └──── provider (github|google) │    tokenHash
   name                          providerId               │    userAgent
                                 email                    │    expiresAt
                                 createdAt                │
                                                          │
   one user → many identities (one per linked provider)   │
   one user → many sessions   (one per device/login)      │

   Password user:    users row, no identities row
   GitHub-only user: users row (password=null) + 1 identity row (github)
   Linked account:   users row + 2 identity rows (github + google)

The identities table is the join. findOrCreateUser is the only function that touches it, and its job is exactly three branches: "already linked → reuse user", "verified email matches existing user → link to that user", "neither → create new user + create identity." Get those three right and everything else is the same JWT plumbing as before.

🔄 ROLLING-SESSION CAVEAT

Every dev hits redirect_uri_mismatch at least once and forgets why. The cause is always the same: the URL your backend sends (${OAUTH_REDIRECT_BASE}/auth/<provider>/callback) is not byte-for-byte identical to what's registered on the provider's console. Trailing slash, wrong port, http vs https — all count as different. The provider's check is strict string equality, not URL normalisation.
