JWT: access vs refresh, secrets, and the leakage attack

Two independently-signed tokens with two different secrets. The access token (jwt.sign({ id: user.id, ... }, JWT_ACCESS_SECRET, { expiresIn: '15m' }), backend/index.js L92) is short-lived and stateless. The refresh token (jwt.sign({ sessionId, id: user.id, ... }, JWT_REFRESH_SECRET, { expiresIn: '7d' }), L93–96) is long-lived and carries a sessionId that /refresh checks against a server-side row in db.sessions (L131). authMiddleware trusts a request only if jwt.verify(token, JWT_ACCESS_SECRET) succeeds (L42).

Anatomy of a JWT — three pieces, only one is "secret-y"

A JWT is a single string with three parts separated by .

     HEADER          .          PAYLOAD          .       SIGNATURE
─────────────────       ────────────────────         ───────────────────
eyJhbGciOiJIUzI1Ni…     eyJpZCI6MTc3ODE4Nj…          XRXWJcLz5L5kN4unA2…

 base64url(JSON)         base64url(JSON)             HMAC-SHA256( header
 { alg, typ }            { id, email, iat, exp }       + "." + payload,
                                                       SECRET )

 PUBLIC                  PUBLIC                       PROVES authorship
 (anyone can decode)     (anyone can decode)          (only the holder
                                                       of SECRET could
                                                       have produced it)

The header and payload are base64-encoded, which is not encryption — it is a reversible reformatting. Anyone with the token can decode them with no key. Try it in Node yourself:

node -e 'console.log(Buffer.from(
   "eyJpZCI6MTc3ODE4NjI1MjQwNCwiZW1haWwiOiJ0ZXN0QHRlc3QuY29tIn0",
   "base64").toString())'
// → {"id":1778186252404,"email":"test@test.com"}

That payload was decoded with zero secret. The signature is the only part the secret is required for — and even the signature does not hide anything; it proves something.

What the signature actually does (and doesn't do)

Suppose an attacker copies a real token and tampers with the payload,
trying to escalate from id=42 to id=1 (admin):

   ORIGINAL:   header . { id: 42 }    . sigA   ← server-issued, valid
   ATTACKER:   header . { id: 1  }    . sigA   ← payload changed,
                                                 sigA kept (they cannot
                                                 produce a new signature
                                                 without the SECRET)

   server: jwt.verify(token, SECRET)
        1. recomputes signature for the NEW header+payload
        2. expected = HMAC-SHA256(header + "." + { id: 1 }, SECRET)
        3. expected ≠ sigA  →  throws  →  401

The signature doesn't conceal the data. It makes any change to the data
visible the moment the server re-checks it.

Stateless verification — no database touch on every request

The expiry (exp) is a claim baked into the signed payload. Because tampering with it breaks the signature, the server can trust the embedded exp as-is. Both checks happen with just the token + the secret:

authMiddleware(request):
  ┌────────────────────────────────────────────────────┐
  │ token = request.headers.authorization.split(" ")[1]│
  │                                                    │
  │ jwt.verify(token, JWT_ACCESS_SECRET):              │
  │   (1) recompute HMAC-SHA256(header+payload, SECRET)│
  │       must equal part 3?      → tamper check       │
  │   (2) read exp out of payload                      │
  │       must be in the future?  → expiry check       │
  │                                                    │
  │ ZERO database calls. The token carries everything. │
  └────────────────────────────────────────────────────┘

The unavoidable trade-off: you can't un-issue a JWT

Statelessness is the speed win — and the limitation. Because nothing server-side records that a particular access token exists, nothing server-side can revoke it before its embedded exp passes:

min 0   user logs in    →  access token T (valid 15 min) returned
min 2   admin BANS them  →  users row marked banned in db.json
min 3   banned user makes a request with T
        authMiddleware:
          signature valid       ✅
          exp not yet passed    ✅
          → REQUEST SUCCEEDS    ← server has no way to know

The server didn't store T anywhere, so it can't "delete" it.
Up to ≤ 15 minutes of usable access after the ban. That is
the cost of statelessness — accepted, not solved.

Why the architecture is short-access + revocable-refresh

The fix is structural, not a smarter check inside authMiddleware:

┌────────────────────── access token ──────────────────────┐
│  short (15 min), stateless, NOT revocable                │
│  Damage window if user is banned/compromised: ≤ 15 min   │
│  In exchange: zero DB lookup on every authenticated req  │
└──────────────────────────────────────────────────────────┘

┌────────────────────── refresh token ─────────────────────┐
│  long (7 days), backed by a row in db.sessions           │
│  /refresh checks: jwt.verify  AND  sessions row exists   │
│      AND  sessionId matches  AND  tokenHash matches      │
│                                                          │
│  Revocation = DELETE the sessions row:                   │
│    POST /logout            → delete this session         │
│    DELETE /devices/:id     → delete a specific session   │
│    POST  /logout-all       → delete all of user's rows   │
│                                                          │
│  Next /refresh call after that → no session row → fail   │
│  → access token expires within 15 min → permanently out  │
└──────────────────────────────────────────────────────────┘

Two layers, two jobs. The access token gives you cheap statelessness most of the time; the refresh token gives you a place you can revoke, bounded by a tiny worst-case lag.

What a leaked JWT_ACCESS_SECRET actually allows

Without the secret:                With the leaked secret:
─────────────────────────          ─────────────────────────
attacker must steal an             attacker runs locally:
already-issued token from
a real user's browser                jwt.sign(
                                       { id: anyUserId },
                                       leakedSecret,
                                       { expiresIn: '15m' }
                                     )

Bound by:                          Bound by:
 • that one user                    • nobody — they can mint a
 • whatever access that user          token for ANY user, including
   actually has                       admin
 • the token's own exp              • no password needed
                                    • the server cannot distinguish
                                      this from a legitimate token —
                                      the signature is mathematically
                                      valid

That is why the secret lives in .env, never in code, never in a commit, never shared with the frontend; and why access and refresh use different secrets — a leak of one shouldn't grant the other.

⚠️ IMPORTANT

Common misread: "A JWT is encrypted, so the payload is hidden from the user."

Actually: a JWT is signed, not encrypted. The payload is base64url-encoded, which is a reversible reformatting any tool (or one line of Node) can decode with no key. If you put a card number, a password, or any secret in the payload, you are publishing it to every holder of the token.

Why it matters: safe contents for a JWT payload are identifiers and claims (user id, role, exp) — never anything that would be a leak if read aloud.

⚠️ IMPORTANT

Common misread: "The signature hides the payload from tampering."

Actually: the signature doesn't hide data — it makes data tamper-evident. Attackers can freely edit the payload (it's base64), but they can't recompute a matching signature without the secret, so the server's jwt.verify detects the change and throws.

Why it matters: "tamper-evident, not data-hiding" is the precise mental model. It's why jwt.verify is the entire defence — skip it and a token's payload becomes user-editable.

⚠️ IMPORTANT

Common misread: "If we need to ban someone, the server can just invalidate their JWT."

Actually: an unexpired access JWT cannot be revoked — the server has no record of it to delete. Verification is purely (signature ok? exp in future?) using only the token + secret. The only fixes are: wait for exp, or move state server-side (which is exactly what the refresh-token + sessions table does).

Why it matters: the inability to revoke is the design's defining trade-off — making the access token short (15 min) and adding a revocable refresh layer is the answer, not an "extra feature."

⚠️ IMPORTANT

Common misread: "A leaked JWT_ACCESS_SECRET isn't that bad — an attacker still needs a password or DB access."

Actually: the secret is the only thing standing between an attacker and a valid token. With it, the attacker runs jwt.sign({ id: <anyone> }, leakedSecret) locally and produces a token authMiddleware will happily accept as any user — no password, no DB access needed, and the server cannot distinguish forged from legitimate.

Why it matters: it's why the secret lives in .env, never in code, and why access ≠ refresh secret — a leak of one shouldn't grant the other.

🔄 ROLLING-SESSION CAVEAT

The reason the refresh token also checks a server-side sessionId (so it can be revoked, unlike the stateless access token) was made near a session boundary. Without it you'd "explain" JWT as fully stateless and miss why /logout and /devices can exist at all.
