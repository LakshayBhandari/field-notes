Cursor pagination, the sliding window44Com

This is the GET /api/conversations/:id/messages route from the 44Com server — history, oldest-first, paginated:

const { limit = '50', cursor } = request.query as { limit?: string; cursor?: string };

const messages = await prisma.message.findMany({
  where: { conversationId: id },
  orderBy: { createdAt: "asc" },        // oldest-first
  take: parseInt(limit),                // page size
  cursor: cursor ? { id: cursor } : undefined,  // where to resume
});

const nextCursor = messages.length > 0
  ? messages[messages.length - 1].id    // last row of THIS slice
  : null;
return reply.code(200).send({ messages, nextCursor });

take = how many, cursor = where to start. Each request runs a brand-new query with a different cursor, so messages is a different slice of the table every time — a window that slides forward:

Page 1 (no cursor):  [ m1, m2, m3 ]   nextCursor = m3
Page 2 (cursor=m3):  [ m4, m5, m6 ]   nextCursor = m6
Page 3 (cursor=m6):  [ m7, m8, m9 ]   nextCursor = m9
Page 4 (cursor=m9):  [ m10 ]          nextCursor = m10 or null

The client's loop is a breadcrumb trail: each page's nextCursor becomes the next request's cursor (m3 → m6 → m9 → …). When the client sees nextCursor: null (or an empty list), it stops.

⚠️ IMPORTANT

Common misread: "messages.length is always 3 on full pages, so how does nextCursor ever change?" — reading the array as one fixed list you page over in memory.

Actually: messages is thrown away and rebuilt from a fresh DB query each request. The length stays 3, but which 3 rows differ, so messages[messages.length - 1] — the last row of this slice — is m3, then m6, then m9. length - 1 computes an index (2); the value there changes because the window slid.

Why it matters: the cursor isn't derived from the count — it's derived from which rows you just fetched. Confusing "same length" with "same data" is what makes cursor pagination feel like magic instead of a plain moving window.

🔄 ROLLING-SESSION CAVEAT

A raw Prisma cursor: { id } is inclusive — it returns the cursor row too, so page 2 would repeat the last row of page 1. Add skip: cursor ? 1 : 0 to skip the cursor row itself. The 44Com route was missing this at first — if you see a duplicated boundary message, that's why.
