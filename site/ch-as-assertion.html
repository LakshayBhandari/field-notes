TypeScript as does no runtime check

In the 44Com routes, request bodies were first read like this:

const { visitorId } = request.body as { visitorId: string };

as is a type assertion — a promise you make to the compiler, not a check. It tells TypeScript "trust me, request.body is this shape" and then vanishes completely at runtime. TypeScript compiles to plain JavaScript, which has no types, so there is no code that verifies anything. Send {} and visitorId is undefined — TypeScript stays silent, Prisma throws, and you get a 500.

What actually validates is a Fastify JSON schema attached to the route — it inspects the real incoming JSON and rejects bad input with a 400 before your handler runs:

app.post("/api/conversations", {
  schema: {
    body: {
      type: "object",
      required: ["visitorId"],
      properties: { visitorId: { type: "string" } },
    },
  },
}, async (request, reply) => { /* handler only runs on valid input */ });
⚠️ IMPORTANT

Common misread: reading request.body as { visitorId: string } as if it validates the body, or that a value is a string because you asserted it.

Actually: as is erased at compile time — it changes what the compiler sees, never what's there. request.body is genuinely unknown bytes from the client; as just paints a type over them without looking. Runtime safety comes from a schema (Fastify), or a parser (Zod), or a manual if — something that runs and inspects.

Why it matters: the gap between "TypeScript is happy" and "the input is actually safe" is where 500s and injection bugs live. Assert for convenience at the boundary, but validate for safety — they are not the same tool.
